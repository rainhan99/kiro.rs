## 变异测试

这一轮对关键守卫共施加 **26 个变异**，其中 **7 个存活**——每一个存活都暴露了测试的空洞，
而不是代码的冗余。修正后全部被抓住。存活的那 7 个及其暴露的问题：

1. 协调器「已提交后不得再开尝试」：断言只写了 `is_err()`，被**账本自己**那道守卫接住了。
   改为钉住协调器自己的措辞。
2. 执行器的 SSRF 检查：原测试用**字面量私网 IP**，被端点构造拦住了；删掉连接前的 DNS
   解析检查照样全过。补了 `localhost` 那条（走 /etc/hosts，离线成立）。
3. 「算不出价时用 0 顶替」：原测试喂的是缓存报不全的用量，`normalize_usage` 在上一层
   就返回 None，够不到定价分支。改用「上游做了 1 小时缓存写入而运维没给这一项定价」。
4. 入口的 `is_managed` 快路径：删掉行为不变，因为 `plan_for` 在下游同样返回 NotManaged。
   它是快路径不是守卫，注释改成如实说明。
5. 「4xx 也换路」：原测试直接调 `handle`，**根本没经过中间件**。补了穿中间件的测试，
   顺带查出预留泄漏（见下）。
6. 「额度按浮点往返」：样例值 `0.0169543708291874` 恰好能被 f64 逐位往返，等于什么都没测。
   换成 18 位小数的值。
7. 「先换快照再写盘」：配置写盘失败根本没有测试。补上后钉住了那条顺序。

## 复核中发现并修掉的缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 规格头号场景端到端走不通：Kiro 路交出去后失败直接回客户端，配好的备路永不被试 | 备路形同虚设 |
| 2 | `validate_max_tokens` 在用量汇聚点建立**之前**返回 400，而释放预留的正是它 | 反复发坏请求可占满并发名额 |
| 3 | `SendError::Refused`（请求根本没发出）被当成不可重试的上游失败 | 回客户端 400「你的请求有问题」，且不再试别的路 |
| 4 | 已删 Key 的 id 会被重新分配（`next_id` 按存活 Key 推算） | 新 Key 继承前一个同 id Key 的余额与历史 |
| 5 | `NativeUsage.raw` 存整条上游响应，经结算进账本再由管理接口读出 | 模型输出与工具参数泄露给任何能看管理面的人 |
| 6 | 原生积分若沿用遗留导入的 12 位截断规则 | 少收钱，且破坏「原生 credit 逐位往返」 |
| 7 | 随机路由下 Kiro 自身粘性未关 | 第一次选中的凭据接管整个会话，"随机"只在第一次生效 |

## 明确**不**声称的事

- **没有打开过浏览器。** 管理界面没有做过视觉检查或交互验证。前端只验证到
  `bun test`、`tsc -b`、`bun run build` 通过这一层；路由预览是通过 API 验证的，不是通过渲染页面。
- **没有部署。** 没有向任何环境发布，没有改动现网配置或凭据。
- **没有真实上游往返。** 所有上游都是本地回环替身或测试替身。因此：
  - 没有观测到任何**原生缓存节省**，也不从模拟数据推断它；
  - 分片后的工具结果能否被 Kiro 接受**未经验证**（该特性默认关闭）；
  - Kiro 路的**成功侧**结算没有端到端跑过——它需要真实凭据。金额换算由
    `credits_to_amount` 的往返测试单独钉住，失败侧（释放）有端到端测试。
- **用量与定价的上游文档**未在本次实现中重新核对；价目表由运维在配置里声明，
  网关只做算术，不内置任何供应商价格。
