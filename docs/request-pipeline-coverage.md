# 原始三阶段需求覆盖核对

结论：**三个阶段的全部条目均已处理完毕（阶段 1 于 2026-09-17，阶段 2 与 3 于 2026-09-18）。** 阶段 1 的四项按「量具 → 账单 → 分类 → 补救」一条链交付，spec 见 `docs/superpowers/specs/2026-09-17-request-pipeline-phase1.md`。阶段 2 的 spec 见 `docs/superpowers/specs/2026-09-18-request-pipeline-phase2.md`，按「观测 → 聚合 → 准入 → 恢复」的顺序交付：先留下上游已经告诉我们、但一直被丢弃的东西，再从本来就会发生的流量里聚合，之后才让上限去拦请求、让分类明确的拒绝被修正一次。顺序本身是这一阶段的实质——反过来做就是把猜测升级成门禁。阶段 3 的推理算法没有因此自动补齐。

本表根据工作树实际调用路径核对；没有发送 Kiro 测试流量。

## 不应混为一谈的验收条件

- 原文可恢复 ≠ 模型已读取全部原文 ≠ 与全量内联具有相同推理效果。
- 字节 Budget Report ≠ token Budget Report；`maxInputTokens` 解析存在 ≠ 已参与 admission。
- 静态 cachePoint 或指纹一致 ≠ 真实命中；只有实际完整上游 native usage 支持 cache read/write 结论。
- Web 配置已保存 ≠ 当前进程已生效；本轮不做服务重启或真实配置变更。
- 语义摘要/增量记忆/Map-Reduce 可能丢细节；即便后续实现，也不能未经任务级质量验证就叫“不降智”。

三阶段清单至此走完，但**「不降智完整版」这个标题不能照单全收**：分块处理已实现，且实现得尽可能诚实（模型显式调用、带区间溯源、合并在模型自己上下文里、代价写在四处），但它在机制上就是降智的——切块后没有任何一轮同时看到超过一块。它是「原文放不下时的一种处理方式」，不是「不降智」。真正无损的路径始终是 artifact 原文按需读取。

任何长度恢复都不能盲目原样重发、自动降级模型或启动线上阈值二分。

阶段 3 交付后新增的已知边界：分块处理的降智是结构性的，不可通过实现质量弥补；某个任务用分块得到的答案是否够好，是对该任务的判断，本仓库不替运维做这个判断，也没有任何离线结果能充当「答案质量」的证据。按需工具发现虽不移除任何工具，但模型是看着名称与描述而非完整 schema 做的选择，这可能影响选择质量，并且会增加轮次。

阶段 2 交付后新增的已知边界：写死的模型名窗口表**仍在**把百分比换算成上报给客户端的 `input_tokens`，本阶段刻意没有换掉它——换成另一个未经检验的数字只是换一个猜测，正确做法是先让校准积累出证据，再由运维决定。因此 `contextUsagePercentage × 窗口表` 的既有误差仍然存在，只是现在它与声明上限、原生用量并列可见了。校准的隐含分母是观察值不是上限，样本少或跨度大时不可采信。准入误拦的代价真实存在，这是它默认关闭的原因。恢复成功一次不证明分片形状被普遍接受。

阶段 1 交付后新增的已知边界：`lossless-chunks` 的上游接受性只能由真实业务流量确认，离线通过不等于上游接受；token 分项是估算，与原生 `metadataEvent.tokenUsage` 不可混用；`maxInputTokens` 只读该凭据已缓存的模型列表，不触发刷新，因此冷启动期间会显示未知。
