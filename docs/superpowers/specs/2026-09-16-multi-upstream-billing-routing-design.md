# 多上游、独立计费账户与可切换粘性路由

日期：2026-09-16

状态：用户已批准实施（“开干”）。本文是验收目标，不是已实现功能清单；开发仅做本地提交与离线验证，不发真实上游请求、不部署。

## 1. 已确认的目标

- 采用方案 B：一个客户端 Key 可配置独立的 Kiro 积分、人民币、美元额度账户；不同单位不相加、不隐式兑换、不互相透支。
- 保留 Kiro 上游，增加 Anthropic-compatible、OpenAI-compatible 上游；支持自定义 URL、密钥、模型、Token 单价和缓存单价。OpenAI 的 Chat Completions、Responses 分别声明能力，不假定两者可互换。
- 上游成本与下游收费分开配置、记录和展示。Kiro 上游的额度始终显示为积分，不显示为美元。
- 下游请求公共模型别名，例如 `opus5`；一个别名可以绑定多个上游及其真实模型 ID。自动切换无需客户端更换模型名。
- 配置上游级权重和模型绑定级权重。Kiro 不可用或积分耗尽时，可以切换到符合条件的备用上游。
- Web 提供“会话粘性 / 加权随机”选择，默认会话粘性；配置必须真正影响后端调度，可观察、可测试。

以下具体默认值与实现边界是本设计的建议，随本文件一起审阅。

## 2. 代码现状与改造边界

- `src/model/config.rs` 的 `CustomModel` 目前只有一个 Kiro `backend_id`，不是多上游模型注册表。
- `src/anthropic/router.rs` / `middleware.rs` 的运行状态以 `KiroProvider` 为中心。现有 OpenAI 入口是下游协议兼容入口，不等于原生 OpenAI 上游。
- `src/kiro/session_affinity.rs` 目前只保存会话到 Kiro 凭据的进程内绑定；现有 `priority` / `balanced` 是 Kiro 账号池策略，`balanced` 不是按权重随机。
- `src/admin/client_keys.rs` 在认证时按 `total_credits >= max_credits` 全局拒绝请求。这会阻止积分用尽后使用仍有金额额度的备用路由，必须拆开身份校验与路由额度准入。
- 现有统计可被“重置统计”清零，存储方式不适合作为新的财务账本。`traces.db` 有保留期，也不能作为账本。
- 现有缓存说明中存在“同 profile 必定共享缓存”的确定性文案；统一改为待原生证据验证，不能将粘性命中等同于缓存命中。

保持前面已完成的请求管线、Kiro 原文读取工具和积分展示改动。本设计不宣称补齐 `docs/request-pipeline-coverage.md` 中尚未实现的全部阶段。

## 3. 三个实现选择

| 选择 | 优点 | 代价 / 限制 |
| --- | --- | --- |
| 只扩展现有 Kiro 账号调度器 | 改动表面较小 | 会把协议适配、跨币种额度、Kiro 凭据状态混在一起，不采用 |
| 独立统一路由层 + 协议适配器 + 账本（采用） | 别名、策略、计费边界一致；可离线验证 | 需要调整公共入口，但 Kiro 内部管线可保留 |
| 引入独立外部网关服务 | 可以分开部署 | 新增运维、密钥与账务同步成本，本次不采用 |

目标部署边界为现有单实例服务与本地 SQLite；不承诺多副本共享粘性或分布式额度强一致。账本、路由、协议适配器各自独立测试，通过一个请求上下文关联，不扩展支付、充值或自动汇率系统。

## 4. 路由对象与权重

### 4.1 核心对象

- `Upstream`：ID、名称、协议类型、基础 URL、服务端凭据引用、启用状态、`weight`、连接限制。Kiro 类型引用现有凭据池与分组，不复制凭据。
- `PublicModel`：公开别名、展示信息、路由模式覆盖值、粘性 TTL 覆盖值。
- `ModelBinding`：公共别名、上游 ID、真实模型 ID、`priorityTier`、`weight`、能力、上游成本价版本。
- `ClientBillingPolicy`：Key 可用的别名/上游范围，以及每个别名、计费单位的下游价表和明确的路由计费规则。
- `BudgetAccount`：Key、计费单位、额度周期、上限、已确认使用、预留、待核算状态。一个请求的下游结算只能选择一个账户。

每条可用的 Key/模型/路由计费规则必须唯一确定结算单位和价表；不根据哪个账户还有余额临时猜测币种。管理员可以显式为 Kiro 配置积分结算、为备用 API 配置金额结算；页面保存时展示切换后的单位变化。

### 4.2 选择顺序

先过滤身份授权、启用状态、健康状态、模型与上下文能力、价格完整性、对应额度账户，之后才使用优先级和权重。

- `priorityTier` 越小越优先。默认 Kiro 为主组 `0`，备用 API 为组 `1`。这是明确的主备策略，不用“大权重”模拟主备。
- 同组有效权重 `W = upstream.weight × binding.weight`。两个权重都为整数，范围 `0..10000`；任一个为 `0` 表示该绑定不参与新调度，也不继续保持粘性。
- 权重仅在同一优先级组的合格候选中比较或抽样。候选数量不能改变组间优先关系。
- Kiro 绑定引用凭据池时，先尝试池内合格账号；一个账号没积分不等于整个 Kiro 池耗尽。
- 同一公共模型不允许重复的上游/真实模型/分组绑定，避免靠重复配置意外放大权重。

`opus5` 只是下游别名，不代表任意上游都存在同名模型，也不构成质量等价保证。协议名称与实际模型系列分开保存。

## 5. Web 路由模式的精确定义

Web 在“设置 → 上游与路由”提供全局默认的两段式选择；每个公共模型可选择“继承全局 / 会话粘性 / 加权随机”。避免使用一个语义不明的开/关按钮。

| 行为 | 会话粘性 `sticky`（默认） | 加权随机 `weighted_random` |
| --- | --- | --- |
| 首次请求 / 没有有效绑定 | 最优可用组中选有效权重最高者 | 最优可用组中按 `W / ΣW` 抽样 |
| 同会话后续请求 | 绑定仍合格则沿用 | 每个新的外部请求重新抽样 |
| 同权重 | 优先较少在途请求，再按稳定 ID 排序 | 相同权重拥有相同抽中概率 |
| 上游失效 | 排除失效目标，重新按组和权重选择 | 排除本次失败目标，重新抽样 |
| 主上游恢复 | 原备用绑定仍合格时不主动抢回；新会话可回主上游 | 后续请求重新选择最优可用组 |
| 缓存含义 | 减少无谓换路由，但不保证缓存命中 | 可能增加冷缓存；费用随原生用量变化 |

一次抽样对应一个新的客户端请求，不对应每个 Token、SSE chunk 或内部工具轮次。一次尝试及其内部工具循环固定使用选定的适配器和路由；故障切换仍受第 7 节限制。

### 5.1 会话身份与绑定范围

- 首选经过格式和长度校验的显式会话标识。支持网关约定的 `X-Session-Id`，以及现有客户端中能够明确解析出“会话”含义的字段；不把普通用户 ID、请求 ID、billing nonce 或 `amz-sdk-invocation-id` 当作会话 ID。
- 绑定键至少包括租户/Key ID、公共模型别名、会话标识的哈希。原始 Key、密钥、对话全文不放进绑定键或普通日志。
- 绑定值包含上游、模型绑定、实际凭据、必要的 profile/端点标识和版本。任何安全范围、模型能力、账户额度变化都重新检查。
- 没有可靠会话 ID 时，报告 `no_session_id`，按无绑定规则调度；不把同一 Key 的所有对话捆成一个会话，也不宣称实现会话粘性。页面提供客户端接入说明。
- 默认 TTL 3600 秒，范围 60..86400 秒；成功完成请求后续期。此处沿用现有单实例、内存、有容量上限的行为：重启或淘汰可能丢失绑定，必须重新选路由。
- 同会话并发首请求使用短临界区生成临时路由租约，不锁住整个网络调用；不同额度预留仍分别执行。只由实际成功的尝试提交正式绑定；版本校验防止较早的失败请求覆盖新绑定。

### 5.2 与已有 Kiro 策略及配置变更的关系

- 统一路由层决定跨上游绑定；Kiro 适配器继续负责池内可用性，不允许两层互相覆盖已经选定的合法绑定。
- 新模式为 `weighted_random` 时，跨上游会话绑定被忽略，Kiro 内部会话粘性也对该请求关闭。Kiro 池内首次选号仍使用其明确标注的账号池策略，不把旧 `balanced` 偷换成加权随机。
- 旧 Kiro 粘性与账号策略保留给尚未迁移的旧模型；新页面明确作用范围，禁止出现两个互相矛盾的有效开关。
- 配置有版本号、乐观并发校验、原子持久化。保存后热更新，对新请求生效；在途请求使用入场时的配置和价格快照，不打断或重新定价。
- 权重调整不强制迁移仍合法的粘性会话；禁用、权重归零、删除绑定会使后续请求重选。模式切换提升路由策略代次，旧代次绑定不在切回粘性时突然复活。
- TTL 调整只影响后续写入和续期；页面说明这一点。展示已保存版本、运行版本和生效状态。

## 6. 单位、价格、额度与结算

### 6.1 单位不能混用

计费单位采用显式类型：`KiroCredit`、`Money(CNY)`、`Money(USD)`。限额 `null` 表示不限，`0` 表示不允许消耗；没有对应账户与价格配置的路由不能成为付费备用路由。

- Kiro 上游成本：原生 metering 积分。账户余额查询是可用性线索，不替代单次消耗证据。
- 原生 API 上游成本：原生使用量乘配置的上游价表，是按配置计算的成本，不冒称供应商账单实际扣款。
- 下游积分计费：只允许有原生 Kiro 积分证据的 Kiro 请求。不得给直连 API 凭空创造“Kiro 积分”。
- 下游金额计费：原生可核实 Token 使用量乘独立的下游价表；可用于 Kiro 或原生 API。上游 USD 成本与下游 CNY 售价各自核算，不需隐式换汇。
- 旧 Key 默认保持积分计费；新建或变更计费单位需创建独立账户，不能改标签后把已有积分数字当金额。

### 6.2 Token 归一化与价格

价格统一以“每百万 Token”的十进制数配置，区分普通输入、输出、缓存读取、缓存写入；上游支持不同写入 TTL 时分别定价。币种是价表必填字段。已知不支持的计费类别标记为“不适用”，支持但漏配价格时阻止启用，不能默认为免费。

适配器保留原始 usage 和字段来源，输出互不重叠的规范化桶。供应商报告输入总量包含缓存时，按该协议的定义扣除其子集；排除缓存时则直接使用。不得将缓存 Token 同时按普通输入与缓存价格收费，也不得假设所有 OpenAI-compatible 服务采用同一种 usage 结构。

计费使用精确十进制或定点运算，禁止二进制浮点金额。存储、计算、预留保留子分精度，展示时才格式化；溢出、负数、非法值拒绝。逐个类别保留计费数量、价格版本和计算结果，不能用总 Token 乘一个模糊平均价。

只凭真实 usage 确认缓存命中和计费。`confirmed`、`estimated`、`missing` 明确区分；缺失字段不按零处理，估算不得伪装原生证据。不能可靠归一化或还有非 Token 计费项目的路由在启用时明确限制能力，不能漏计后宣称完整核算。

### 6.3 账本与额度准入

- 独立 SQLite 账本保存账户、周期、预留、请求、上游尝试、使用量证据、结算和调整记录；不随 Trace 保留期清理。
- 认证只验证 Key 身份、禁用和访问范围。候选路由的对应账户余额检查及额度预留在数据库事务中执行。
- 请求 ID、尝试 ID、结算 ID 分开，数据库唯一约束与事务保证同一结算不重复入账；内存布尔变量不足以保证重启后幂等。
- 能给出可靠消耗上界的金额请求，预留包含输入、输出上限、缓存类别及内部轮次的保守上界；最终按确认量结算，多余预留释放。不能给出可靠上界则不得标为“硬额度保证”。
- Kiro 原生积分只能事后得知时，使用显式软上限与在途并发控制，并提示仍可能超额；不使用虚构积分预估宣称严格不超限。不能限界的请求只在明确允许软额度的账户策略下放行。
- 缺失 usage、结果不明或进程崩溃留下的尝试进入待核算，不能自动零结算或无条件释放全部风险占用；重启恢复扫描，人工调整需理由与审计。限制待核算和在途数量，避免无限透支。
- 上游每次实际尝试分别记成本。未向下游提交有效响应的失败尝试不自动转嫁客户；成功返回或已经提交有效响应后中断的尝试，按其确认用量结算一次。服务该响应的内部工具轮次归入同一逻辑请求并在明细展示，不再作为独立客户请求重复计费。
- 跨单位重试前，将尚未向客户端提交有效响应的失败尝试记入上游成本；usage 不明则该成本待核算，但不因此向客户扣费。释放该尝试的下游预留，再独立检查目标账户；不能把一笔积分预留挪成美元预留。已经提交有效响应的尝试不再自动跨上游重试，其客户结算仍归原账户。
- “重置统计”只处理分析视图，不能清账本或恢复财务额度；额度周期切换和人工调整是单独的、有审计的操作。

## 7. 故障转移与不中断编程的边界

公共入口在 Kiro 专用转换之前进行路由。保存原始请求和可重放的规范化对话；选择适配器后才生成其专用 payload。不得把 Kiro 内部 artifact 引用、cache point 或认证头直接发给其它供应商。

- 额度耗尽：要求有结构化上游证据，按准确的账号/订阅/上游范围标记；余额查询失败或过期本身不是耗尽证据。
- 429：尊重服务端重试提示，短暂冷却并在总预算内考虑其它合格目标，避免重试风暴。
- 网络错误与 5xx：有限重试；Kiro 池内与跨上游共享总尝试数和时间预算，不能层层相乘。
- 普通格式错误不盲目换供应商。长度 400 单独分类：只允许能力和预算确认可接收的完整等价请求转移，或使用已批准的无损管线；不裁掉上下文、降低推理预算来掩盖失败。
- 兼容性检查包含工具调用/结果配对、图片、上下文上限、推理或签名块、服务端会话状态、内置工具语义。无法完整转换的目标排除并给出原因，不静默丢字段。
- 只携带供应商私有 conversation/response 引用、没有可重放历史时，不宣称能无损跨供应商接续。
- 默认只允许明确配置且满足能力要求的真实模型；变更模型系列的备用目标需管理员明确允许。别名相同不代表效果相同。

自动切换限于尚未向客户端提交第一个有效响应事件时；提交了响应身份、正文或工具调用后，不拼接另一个上游的输出。断流按客户端协议报告失败，下一次客户端请求重新判断路由。不能承诺网络中断时每条已输出的流都无缝续写。

心跳等无语义数据不作为成功内容。即使尚未输出，也不得自动重放可能已经执行的有副作用工具；只在重放安全性可确认时重试。客户端重发不是天然幂等，只有满足显式幂等约定的请求才能去重，不能用相同 body 哈希抹掉合法重复调用。

## 8. 协议适配与安全边界

统一适配器负责请求转换、流式事件规范化、错误分类、原生 usage 提取；路由层只消费这些接口，不内嵌各供应商 JSON 判断。

- 能同协议传递的合法字段尽量保留；跨协议转换仅放行已实现并验证的能力。不会将非流式完整响应包装成伪流就宣称实现真正流式直连。
- 上游 URL、路径拼接和 API 版本明确配置；区分基础 URL 与完整端点，防止重复追加 `/v1`。
- 密钥仅存服务端、页面脱敏；不透传下游 Authorization、客户端 Key、Host 或无关动态 header。必要签名/认证头不能简单删掉。
- URL 校验阻止不受控访问内网和元数据服务；本地或私有兼容服务需管理员显式许可的目标范围，重定向不能绕过校验或带走凭据。
- 日志与错误片段脱敏，不记录完整认证头、base64 图片或对话内容来证明长度/缓存。指纹和分项大小足够时使用它们。
- 路由粘性只是稳定选择；缓存隔离范围不凭 profile 或账号名称推定，原生统计缺失时显示未知。

## 9. Web 与可验证配置

页面需要落地以下真实 API 能力，而非仅保存前端状态：

1. 上游管理：协议、URL、凭据、币种、启用状态、全局权重、成本价、支持的接口类型。
2. 公共模型：别名、真实模型绑定、主备组、模型权重、能力限制、下游价表、粘性/随机覆盖设置。
3. 路由设置：全局粘性/加权随机、TTL、保存/生效版本、旧 Kiro 配置作用范围。
4. 客户端 Key：积分/CNY/USD 独立上限、已用、预留、待核算、可访问模型与各路由计费单位；分别展示，不显示混合“总余额”。配置硬/软额度策略和在途限制，清楚提示 Kiro 积分软额度的超额风险。
5. 路由预览：输入 Key 与公共模型及必要能力，无上游网络请求地显示候选、排除原因、所在优先组、有效权重；随机模式展示条件概率，粘性模式展示是否有合法绑定。
6. 请求详情：实际公共别名、真实模型、上游、路由模式、粘性结果、尝试链、失败转移原因、配置与价表版本、客户扣费账户、上游成本与下游费用。
7. 缓存证据：适配器原始 usage 来源，Kiro 原生 `cacheReadInputTokens` / `cacheWriteInputTokens`；粘性命中率与缓存命中率分开。模拟数据明确仅用于本地测试。

保存配置会先验证引用、能力、价格、计费单位与循环/重复关系。提供结构化校验错误。敏感字段不可在路由预览和导出中泄漏。

## 10. 迁移、实施顺序与回退

实施拆成可独立验证的阶段，但直到统一准入、结算和 Web 配置全部就绪才允许启用新的付费路由：

1. 建立类型化单位、版本化配置、独立账本及旧积分数据迁移。旧 `max_credits` 迁为积分额度，`total_credits` 迁为有来源标记的期初使用额；不能伪造历史逐请求证据。迁移幂等并保留备份。
2. 抽出入口认证、规范请求与统一调度，先接现有 Kiro 适配器，用本地桩实现公共别名、主备组、两个权重和两个模式。
3. 接入 Anthropic-compatible 与 OpenAI-compatible 适配器，逐协议验证真实流式转换、原生 usage、错误和重试边界。
4. 完成管理 API、Web 页面、单请求价格快照、审计明细与纯离线路由预览。
5. 完成迁移、并发、崩溃恢复、流式故障回归，再编译交付。真实供应商验证只在用户明确授权后的正常低频业务范围内进行。

旧配置可继续运行原 Kiro 路径；明确迁移为新模型配置后才使用新的覆盖策略。已有明确关闭粘性的设置不能在升级时被无提示改成开启。

运行期禁用新模型绑定可停止新流量，不影响在途结算；不得通过直接降级到不认识新账本的旧二进制继续接收费请求。回退须停止新请求、保留/核对新账本和待核算项，不能覆盖账本或把新金额消费塞回旧积分字段。

## 11. 离线验收标准

默认只运行本地 HTTP/SSE mock 与固定 fixture，不做真实 Kiro 阈值二分、压力测试或批量探测。

- 模式：同会话在 `sticky` 下稳定绑定；新 Key/别名/会话不串绑；缺会话 ID 可见；TTL、重启、并发首请求及模式切换按第 5 节执行。
- 权重：零权重排除；乘积、主备组和并列规则正确；随机器可注入固定种子，做确定性边界测试和本地统计检验，绝不以供应商请求数证明随机比例。
- 切换：Kiro 单账号耗尽先选池内其它账号，池无合格目标后选备用；高权重但无对应额度的候选被排除。备用粘性不在 Kiro 恢复时立即失效。
- 协议：Messages、Chat Completions、Responses 的支持能力、工具配对、图片、取消、usage 与流事件分别有 fixture；不支持的字段/历史明确拒绝或排除目标，不被静默丢弃。
- 流：首有效事件之前安全切换；输出后中断不拼接供应商、不重复执行工具；多层重试不突破共同预算。
- 计费：积分、CNY、USD 隔离；缓存不重复算；价格修改不影响在途；失败尝试成本与客户扣费分离；缺失 usage 待核算；并发预留和重复回调不重复扣款。
- 恢复：事务中断、重启、重复迁移、重复结算、磁盘写入失败、人工调整均可验证；重置统计不能增加财务余额。
- Web：创建、编辑、保存、刷新后读取到相同有效配置；前后端一致验证；模式与权重确实改变本地 mock 的路由轨迹，不只是控件变色。
- 回归：原 Kiro-only 流程、原文 artifact 工具、已有请求管线配置、正确的积分单位展示继续通过测试。

这些测试只能证明本地实现行为。实际 Kiro 缓存改善只能由获准正常流量里的原生统计支持；没有原生证据时结论必须保留为“未验证”。
